# Нативные CPU-диагностики через Native API

[Главная](../README.md) · [Каталог проверок](tests/README.md) · [Сборка и запуск](development.md) · [Runbook](runbook.md)

## Что делает компонента

`CpuFrequencyProbe` — библиотека Native API на C++ для запуска CPU-измерений и сбора доступных сведений о системе внутри процесса 1С. Версия 0.6.0 сохраняет оценку эквивалентных МГц, диагностики 002–011 и системный паспорт через `GetSystemInfo()`. Метод возвращает JSON с ОС и версией ядра, архитектурой, моделью компьютера и CPU, числом логических процессоров и физических ядер, объёмом и доступностью памяти, а также видимыми лимитами cgroup/Job Object, если их раскрывает платформа. Полный пакет 0.6.0 встроен в макет; запуск компоненты в 1С проверен на macOS x86_64.

Это снимок значений, которые возвращают системные API для процесса 1С. В ВМ и контейнере часть значений относится к виртуальной среде или ограничена настройками процесса; недоступные поля возвращаются как `null`. Метод не читает серийные номера, MAC-адреса, диски или видеокарты. Системные API различаются между ОС, поэтому поле может быть недоступно на конкретной платформе.

Результаты — диагностики исполнения конкретного процесса. Они не доказывают первопричину без внешних счётчиков: например, lateness включает таймер и планировщик, длительная нагрузка не считывает температуру, а высокая задержка контрольного потока не даёт длину системной run queue. Недоступные платформенные источники не заменяются догадкой по скорости.

## Пробы и основные метрики

| ID | Код Native API | Измерение | Что сохраняется как основное значение | Ограничение вывода |
|---|---|---|---|---|
| 002 | `CPU_002_INDEPENDENT_INSTRUCTIONS` | Throughput 1/2/4/8 независимых арифметических цепочек при одинаковом общем числе обновлений | `fourChainOpsPerSecond`, `ops/s` | Нет аппаратных PMU cycles/IPC |
| 003 | `CPU_003_WAKE_LATENCY` | Опоздание нативного потока после абсолютного срока `sleep_until` | `p95WakeLatenessNs`, нс | Таймер и ожидание планировщика не разделяются |
| 004 | `CPU_004_READY_QUEUE` | Контрольная работа при заданном числе конкурирующих вычислителей | `p95ControlResponseNs`, нс | Поведенческий сигнал; системная run queue не читается |
| 005 | `CPU_005_CPU_QUOTA` | Текущая CPU-квота и изменение доступных счётчиков throttling при нагрузке | Linux `throttledUsecDelta`, мкс; Windows `configuredCpuRatePercent`, % | Содержимое зависит от ОС и контейнера |
| 006 | `CPU_006_SMT_COMPETITION` | Throughput при конкуренте на SMT-соседе относительно baseline и отдельного ядра | `smtThroughputPercentOfBaseline`, % | Нужны видимая топология и разрешённая affinity |
| 007 | `CPU_007_CORE_MIGRATION` | CPU ID вокруг вычислительных порций и длительность порций после миграции | `migrationCount`, переходы | Не вызывает миграцию искусственно; видит только наблюдённые |
| 008 | `CPU_008_IDLE_RECOVERY` | Первый блок после заданной паузы против медианы прогретых блоков | `firstAfterIdleNsPerUpdate`, нс/обновление | Не читает частоту и состояние питания |
| 009 | `CPU_009_SUSTAINED_SPEED` | Throughput одинаковой нагрузки по последовательным окнам | `medianOpsPerSecond`, ops/s | Не читает температуру и аппаратные power/thermal limits |
| 010 | `CPU_010_INTERRUPT_JITTER` | Распределение длительности калиброванных CPU-порций около 10 мкс и доступные переключения контекста | `p999BlockDurationNs`, нс | Косвенный сигнал: не различает IRQ/softirq и вытеснение планировщиком; на Windows счётчики переключений недоступны |

### Доступность по ОС

| ОС | 002 | 003 | 004 | 005 | 006 | 007 | 008 | 009 | 010 | 011 |
|---|---|---|---|---|---|---|---|---|---|---|
| Linux | Да | Да | Да | cgroup v1/v2 | При доступной SMT-топологии и affinity | CPU ID | Да | Да | Да; счётчики через `getrusage` | Да; steal из `/proc/stat`, если доступен |
| Windows | Да | Да | Да | Job Object CPU-rate, если доступен | При доступной топологии и affinity | CPU ID | Да | Да | Да; без счётчиков переключений | Да; без Linux steal-счётчика |
| macOS | Да | Да | Да | Недоступно | Недоступно | Недоступно | Да | Да | Да; при наличии `RUSAGE_THREAD` | Да; без Linux steal-счётчика |

Даже при поддержке ОС конкретный контейнер/ВМ может скрыть cgroup, SMT-соседа или разрешение affinity. В этом случае JSON содержит доступность и причину. В Linux проба 005 читает квоту и счётчики cgroup, но не изменяет лимит. Windows Job Object сообщает конфигурацию CPU-rate, а не фактическое время throttling.

## Интерфейс Native API

`make native-package` берёт версию из `native/cpu-frequency/CMakeLists.txt` и добавляет её к именам библиотек в `MANIFEST.XML`, например `CpuFrequencyProbe_MacOS64_v0_5_0.dylib`. Клиент 1С распаковывает Native API в `~/.1cv8/1C/1cv8/ExtCompT`; новое имя даёт следующей версии отдельный путь и обходит старый извлечённый бинарник.

Перед подключением кнопки нативной пробы проверяют, загружена ли компонента в текущем процессе (`ПроверитьПодключениеВнешнейКомпоненты`). Если она уже подключена, повторный асинхронный вызов пропускается; если нет — компонента подключается из общего макета. YAxUnit-тесты тоже сначала пытаются подключить компоненту и вызывают установщик только при неудаче подключения, чтобы не показывать диалог установки для уже доступной компоненты. При ошибке установки форма повторяет подключение, а ошибку показывает только если попытка тоже не удалась.

Компонента регистрирует объект `AddIn.CpuFrequencyProbe.CpuProbe` с методами `Measure(BlocksPerSample, Warmups, Samples)` и `GetSystemInfo()`. Положительный первый аргумент `Measure` сохраняет прежнее поведение — оценку эквивалентных МГц. Отрицательные значения `-2` … `-11` выбирают соответствующие пробы; `-1` запускает комплект из десяти. Для 010 `arg1` задаёт число порций (1 000–100 000), `arg2` — целевую длительность порции (5–100 мкс). Для 011 `arg1` задаёт номинальное CPU-окно (100–10 000 мс), а `arg2` — длительность CPU-порции (100–10 000 мкс); по умолчанию — 500 мс и 1 000 мкс. Проба 011 измеряет эффективную долю CPU-времени текущего потока, скорость вычислений, распределение разницы wall/CPU и Linux steal ticks, если они доступны. Steal — агрегатный системный счётчик; host-ready недоступен. Эти числа — внутренний числовой диспетчер для BSL, пользовательские коды и сохранённые результаты остаются именованными `CPU_002_…` … `CPU_011_…`.

Отдельный класс с текстовой командой оказался несовместим с используемой конфигурацией клиента 1С: при создании объект отвечал `Тип не определен`. Строковый аргумент в существующем `Measure` также не подходит: платформа подставляла числовые значения по умолчанию до вызова компоненты. Поэтому используется один зарегистрированный класс и числовые аргументы, которые уже задействованы частотным тестом.

Пример вызова из BSL после подключения общего макета:

```bsl
ПодключитьВнешнююКомпоненту(
    "ОбщийМакет.CpuFrequencyProbe",
    "CpuFrequencyProbe",
    ТипВнешнейКомпоненты.Native);

ИзмерительЧастотыCPU = Новый("AddIn.CpuFrequencyProbe.CpuProbe");
JSONОценкиЧастоты = ИзмерительЧастотыCPU.Measure(1000000, 1, 7);
JSONРезультата002 = ИзмерительЧастотыCPU.Measure(-2, 200000, 5);
JSONВсехДиагностик = ИзмерительЧастотыCPU.Measure(-1, 0, 0);
JSONПаспортаСистемы = ИзмерительЧастотыCPU.GetSystemInfo();
```

Для отдельного теста параметры занимают второй и третий аргументы `Measure`; дополнительные параметры задаются нативными безопасными значениями по умолчанию. Пределы нагрузки и допустимые интервалы проверяются в C++ до запуска.

Пример одной записи JSON:

```json
{
  "schemaVersion": 1,
  "componentVersion": "0.5.0",
  "probeCode": "CPU_003_WAKE_LATENCY",
  "probeName": "003. Задержка пробуждения",
  "available": true,
  "status": "Косвенный сигнал",
  "primaryMetric": "p95WakeLatenessNs",
  "primaryValue": 12345,
  "primaryUnit": "нс",
  "checksum": 42,
  "details": "...",
  "measurements": {"p50WakeLatenessNs": 10000, "p99WakeLatenessNs": 18000}
}
```

Пример паспорта системы (значения условные; поля, которые ОС не раскрывает, могут быть `null`):

```json
{
  "schemaVersion": 1,
  "componentVersion": "0.5.0",
  "system": {
    "name": "Linux",
    "version": "Debian GNU/Linux 12",
    "kernelVersion": "6.1.0",
    "architecture": "x86_64",
    "machineModel": null
  },
  "cpu": {
    "vendor": "GenuineIntel",
    "model": "Пример CPU",
    "logicalProcessorsReportedByOS": 8,
    "physicalCoresReportedByOS": 4,
    "cgroupQuotaCores": 2.0,
    "jobCpuRatePercent": null
  },
  "memory": {
    "physicalTotalBytes": 17179869184,
    "physicalAvailableBytes": 8589934592,
    "processLimitBytes": 4294967296,
    "limitSource": "cgroup v1/v2"
  },
  "scope": "OS-reported values; cgroup and Job Object limits are included when visible. Virtual machines and containers may expose virtual resources"
}
```

Поля памяти указаны в байтах. `cgroupQuotaCores` — видимый лимит CPU в ядрах; `jobCpuRatePercent` — видимый лимит Windows Job Object в процентах.

Форма разбирает ответы CPU-проб и сохраняет 20 результатов в `РегистрСведений.РезультатыПрогонов`: `NCPU002C` … `NCPU011C` для клиента и `NCPU002S` … `NCPU011S` для серверного контекста. Отдельные JSON-снимки клиента и сервера сохраняются в `РегистрСведений.ПаспортаСистем` под тем же ID прогона. Сбор на клиенте выполняется асинхронно; недоступность паспорта не прерывает CPU-диагностики.

Обработка **«ЗапускБенчмарка»** содержит кнопку **«CPU: нативные диагностики 002–011»**. Клиентская часть запускается асинхронно в приложении пользователя, после чего серверная директива повторяет полный комплект в серверном процессе. Одна кнопка создаёт один ID прогона, сохраняет 20 строк CPU-диагностик и по одной записи паспорта в каждом доступном контексте. В клиент-серверной ИБ серверные измерения исполняются в `rphost`; в файловой ИБ серверная директива не создаёт отдельный серверный процесс.

### Повторный прогон на свежем экспорте

Для повторения подтверждённых macOS-прогонов выполните `make export-xml`, затем команды ниже. Каждая создаёт отдельную файловую ИБ и сохраняет отчёты в собственном каталоге. Скрипт удаляет и создаёт заново указанный `IB_DIR`; для сохранения предыдущей ИБ задайте новый путь.

```bash
set -e
make export-xml
make download-yaxunit

PATH="/opt/1cv8/8.5.1.1529:$PATH" \
CLIENT_BIN="/opt/1cv8/8.5.1.1529/1cv8" \
WORKSPACE="$PWD" \
IB_DIR="$PWD/build/ib-local-native06-full-after-export" \
REPORTS_DIR="$PWD/build/reports-local-native06-full-after-export" \
./tools/scripts/build-and-test.sh --mode ibcmd
```

Повтор на актуальном `build/xml` уже выполнен в отдельной сетевой среде с доступом к сервису лицензирования; результат не изменился. Следующий шаг — установить источник сообщения `Цифровая подпись конфигурации неверна` по полному выводу запуска, `platform.log` и журналам поиска лицензии, если платформа их создаёт. Проверка через клиент-серверную ИБ потребует зарегистрировать отдельную тестовую ИБ в RAS и создать БД в PostgreSQL. Эту проверку следует выполнять только в выделенном стенде; для отдельного `rphost` также нужен изолированный клиент-серверный стенд.

### Следующие шаги

1. В выделенном тестовом кластере создать временную клиент-серверную ИБ с уникальным именем, проверить получение лицензии и удалить только созданные для теста регистрацию, БД и роль. Не изменять существующие ИБ и роли.
2. Выполнить тест в изолированной клиент-серверной ИБ с отдельным `rphost`; предыдущая регистрация тестовой ИБ в доступном кластере остановилась на `rac infobase create` с ошибкой формата потока. Запуск в сетевой среде с доступом к сервису лицензирования не устранил ошибку Linux-клиента.
3. Проверить Native API 0.6.0 внутри Windows 1С на Windows-хосте или VM и отдельно проверить macOS ARM64 компоненту, когда будет доступна соответствующая платформа 1С.
4. Если нужен полный перечень оборудования, расширить сбор GPU, накопителей, сетевых адаптеров и модулей памяти; это не покрывается текущим паспортом CPU-бенчмарка.

## Проверки и подтверждённые прогоны

```bash
make native-test
python3 -m unittest discover -s tools/tests -p 'test_*.py' -v
make export-xml
make test-local
```

`native-test` запускает CTest, проверку массива CPU-диагностик от `--all-diagnostics` и проверку JSON-контракта системного паспорта от `--system-info` на текущей ОС. CTest проверяет десять CPU-проб, ограничения аргументов, обязательные метрики и явные статусы доступности. YAxUnit загружает конфигурацию в 1С, вызывает каждую диагностику отдельно, проверяет пакетный клиентский результат и серверное исполнение/запись результата.

27 ноября 2026 года `make native-test` прошёл на macOS ARM64. После добавления CPU_011 CTest и JSON-контракты также прошли для Linux ARM64 CLI в Docker; Linux вернул доступный агрегатный steal-счётчик. Эти прогоны проверяют нативное ядро/CLI, а не загрузку компоненты в 1С на Linux.

Для версии 0.5.0 изолированный YAxUnit-прогон на локальной 1С 8.5.1.1621 завершился успешно: **103 теста, failures=0, errors=0**, macOS x86_64, файловая ИБ. Тест формы напрямую запускает CPU_010 и клиентский/серверный пакет из 18 результатов. Отдельный `rphost` этот прогон не проверяет.

Полный пакет Native API 0.6.0 в изолированной файловой ИБ на 1С 8.5.1.1621/macOS x86_64 прошёл **103 теста, failures=0, errors=0**. Клиентский тест вызвал CPU_011 и проверил 100 порций, эффективную долю CPU и поле steal; форма сохранила 20 клиентских/серверных диагностик и паспорта. Отдельный `rphost` не проверялся.

Дополнительно проверял Linux ARM64 клиент 1С 8.5.1.1529 в одноразовых контейнерах без сети. На копии macOS-ИБ и двух базах, созданных Linux ARM64 `ibcmd`, включая базу на свежем XML, клиент завершился до запуска YAxUnit с сообщением `Цифровая подпись конфигурации неверна`. Один `.lic` файл подключённого read-only license volume не подтверждает успешное получение лицензии; источник сообщения остаётся неизвестным. `xvfb-run` в этом образе зависает до появления процесса `1cv8c`; ручной запуск Xvfb позволил запустить клиента. JUnit не создан, поэтому runtime Native API в Linux 1С пока не подтверждена.

Интеграционный прогон версии 0.3.0 прошёл в файловой ИБ на 1С 8.5.1.1529/macOS x86_64: **102 теста, failures=0, errors=0**. YAxUnit выполнил каждый код CPU_002–CPU_009 отдельно, проверил комплект на клиенте и серверную обработку, а также наличие 16 сохранённых строк. В этом прогоне оценка MHz составила 3198,9 на клиенте и 3196,9 в серверной директиве. В файловой ИБ оба значения относятся к одной машине, а серверная директива не создаёт отдельный кластерный `rphost`. Старый файл компоненты оставался в кэше клиента; версионированный путь из нового манифеста позволил пройти тест без ручной замены кэшированного бинарника. Эти результаты не заменяют runtime-проверку Native API на Linux/Windows.

Платформенные ограничения и обходы сохраняются в [runbook](runbook.md). Лицензии 1С, заголовки SDK и временные отчёты в репозиторий не добавляются.

## Сборка и пакет

Официальные заголовки Native API нужны для библиотек платформ, CLI и unit-тесты собираются без SDK. Полный перечень команд и архитектур — в [development.md](development.md); известные кросс-компиляционные особенности — в [runbook](runbook.md#уже-встречавшиеся-проблемы).


Полный пакет Native API 0.6.0 доступен в [`CpuFrequencyProbe-0.6.0.zip`](../releases/CpuFrequencyProbe-0.6.0.zip); SHA-256 записан рядом. Он содержит Linux i386/x86_64/ARM64, Windows x86/x86_64 и macOS x86_64/ARM64 и встроен в `Template.addin`. Сборка сама по себе не заменяет runtime-проверку в Windows/Linux 1С и отдельном `rphost`.
