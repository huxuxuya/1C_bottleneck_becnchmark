# Нативные CPU-диагностики через Native API

[Главная](../README.md) · [Каталог проверок](tests/README.md) · [Сборка и запуск](development.md) · [Runbook](runbook.md)

## Что делает компонента

`CpuFrequencyProbe` — библиотека Native API на C++ для запуска узких CPU-измерений внутри процесса 1С. Комплект 0.3.0 включает прежнюю команду косвенной оценки эквивалентных МГц и восемь диагностик 002–009. Новые диагностики возвращают измеряемую скорость/задержку, а при отсутствии системного API явно выдают статус `Недоступно`. Они не используют shell, внешние программы или отдельный агент.

Результаты — диагностики исполнения конкретного процесса. Они не доказывают первопричину без внешних счётчиков: например, lateness включает таймер и планировщик, длительная нагрузка не считывает температуру, а высокая задержка контрольного потока не даёт длину системной run queue. Недоступные платформенные источники не заменяются догадкой по скорости.

## Пробы и основные метрики

| ID | Код Native API | Измерение | Что сохраняется как основное значение | Ограничение вывода |
|---|---|---|---|---|
| 002 | `CPU_002_INDEPENDENT_INSTRUCTIONS` | Throughput 1/2/4/8 независимых арифметических цепочек при одинаковом общем числе обновлений | `fourChainOpsPerSecond`, `ops/s` | Нет аппаратных PMU cycles/IPC |
| 003 | `CPU_003_WAKE_LATENCY` | Опоздание нативного потока после абсолютного срока `sleep_until` | `p95WakeLatenessNs`, нс | Таймер и ожидание планировщика не разделяются |
| 004 | `CPU_004_READY_QUEUE` | Контрольная работа при заданном числе конкурирующих вычислителей | `p95ControlResponseNs`, нс | Поведенческий сигнал; системная run queue не читается |
| 005 | `CPU_005_CPU_QUOTA` | Текущая CPU-квота и изменение доступных счётчиков throttling при нагрузке | Linux `throttledUsecDelta`, мкс; Windows `configuredCpuRatePercent`, % | Содержимое зависит от ОС и контейнера |
| 006 | `CPU_006_SMT_COMPETITION` | Throughput при конкуренте на SMT-соседе относительно baseline и отдельного ядра | `smtThroughputPercentOfBaseline`, % | Нужны видимая топология и разрешённая affinity |
| 007 | `CPU_007_CORE_MIGRATION` | CPU ID вокруг вычислительных порций и длительность порций после миграции | `migrationCount`, переходы | Не вызывает миграцию искусственно; видит только наблюдённые |
| 008 | `CPU_008_IDLE_RECOVERY` | Первый блок после заданной паузы против медианы прогретых блоков | `firstAfterIdleNsPerUpdate`, нс/обновление | Не читает частоту и состояние питания |
| 009 | `CPU_009_SUSTAINED_SPEED` | Throughput одинаковой нагрузки по последовательным окнам | `medianOpsPerSecond`, ops/s | Не читает температуру и аппаратные power/thermal limits |

Карточки методик: [002](tests/cpu/002.md), [003](tests/cpu/003.md), [004](tests/cpu/004.md), [005](tests/cpu/005.md), [006](tests/cpu/006.md), [007](tests/cpu/007.md), [008](tests/cpu/008.md), [009](tests/cpu/009.md).

### Доступность по ОС

| ОС | 002 | 003 | 004 | 005 | 006 | 007 | 008 | 009 |
|---|---|---|---|---|---|---|---|---|
| Linux | Да | Да | Да | cgroup v1/v2 | При доступной SMT-топологии и affinity | CPU ID | Да | Да |
| Windows | Да | Да | Да | Job Object CPU-rate, если доступен | При доступной топологии и affinity | CPU ID | Да | Да |
| macOS | Да | Да | Да | Недоступно | Недоступно | Недоступно | Да | Да |

Даже при поддержке ОС конкретный контейнер/ВМ может скрыть cgroup, SMT-соседа или разрешение affinity. В этом случае JSON содержит доступность и причину. В Linux проба 005 читает квоту и счётчики cgroup, но не изменяет лимит. Windows Job Object сообщает конфигурацию CPU-rate, а не фактическое время throttling.

## Интерфейс Native API

`make native-package` берёт версию из `native/cpu-frequency/CMakeLists.txt` и добавляет её к именам библиотек в `MANIFEST.XML`, например `CpuFrequencyProbe_MacOS64_v0_3_0.dylib`. Клиент 1С распаковывает Native API в `~/.1cv8/1C/1cv8/ExtCompT`; новое имя даёт следующей версии отдельный путь и обходит старый извлечённый бинарник.

Компонента регистрирует один объект `AddIn.CpuFrequencyProbe.CpuProbe` с методом `Measure(BlocksPerSample, Warmups, Samples)`. Положительный первый аргумент сохраняет прежнее поведение — оценку эквивалентных МГц. Отрицательные значения `-2` … `-9` выбирают соответствующие пробы; `-1` запускает комплект из восьми. Эти числа — внутренний числовой диспетчер для BSL, пользовательские коды и сохранённые результаты остаются именованными `CPU_002_…` … `CPU_009_…`.

Отдельный класс с текстовой командой оказался несовместим с используемой конфигурацией клиента 1С: при создании объект отвечал `Тип не определен`. Строковый аргумент в существующем `Measure` также не подходит: платформа подставляла числовые значения по умолчанию до вызова компоненты. Поэтому используется один зарегистрированный класс и числовые аргументы, которые уже задействованы частотным тестом.

Пример вызова из BSL после подключения общего макета:

```bsl
ПодключитьВнешнююКомпоненту(
    "ОбщийМакет.CpuFrequencyProbe",
    "CpuFrequencyProbe",
    ТипВнешнейКомпоненты.Native);

ИзмерительЧастотыCPU = Новый("AddIn.CpuFrequencyProbe.CpuProbe");
JSONОценкиЧастоты = ИзмерительЧастотыCPU.Measure(1000000, 1, 7);
JSONРезультата002 = ИзмерительЧастотыCPU.Measure(-2, 200000, 5);
JSONВсехДиагностик = ИзмерительЧастотыCPU.Measure(-1, 0, 0);
```

Для отдельного теста параметры занимают второй и третий аргументы `Measure`; дополнительные параметры задаются нативными безопасными значениями по умолчанию. Пределы нагрузки и допустимые интервалы проверяются в C++ до запуска.

Пример одной записи JSON:

```json
{
  "schemaVersion": 1,
  "componentVersion": "0.3.0",
  "probeCode": "CPU_003_WAKE_LATENCY",
  "probeName": "003. Задержка пробуждения",
  "available": true,
  "status": "Косвенный сигнал",
  "primaryMetric": "p95WakeLatenessNs",
  "primaryValue": 12345,
  "primaryUnit": "нс",
  "checksum": 42,
  "details": "...",
  "measurements": {"p50WakeLatenessNs": 10000, "p99WakeLatenessNs": 18000}
}
```

Форма разбирает эти ответы и сохраняет значения в `РегистрСведений.РезультатыПрогонов` под кодами `NCPU002C` … `NCPU009C` для клиента и `NCPU002S` … `NCPU009S` для серверного контекста. Колонка `КодПробы` использует постоянный код с суффиксом `C`/`S`; JSON целиком не теряется: первичная метрика, контрольная сумма, ключевые параметры и поля измерений помещаются в детали результата. Все нативные показатели получают статус `Косвенный сигнал` при доступности и `Недоступно` в ином случае; они не начисляют баллы.

Обработка **«ЗапускБенчмарка»** содержит кнопку **«CPU: нативные диагностики 002–009»**. Клиентская часть запускается асинхронно в приложении пользователя, после чего серверная директива повторяет полный комплект в серверном процессе. Одна кнопка создаёт один ID прогона и сохраняет 16 строк (8 на контекст). В клиент-серверной ИБ серверные измерения исполняются в `rphost`; в файловой ИБ серверная директива не создаёт отдельный серверный процесс.

## Проверки и подтверждённые прогоны

```bash
make native-test
python3 -m unittest discover -s tools/tests -p 'test_*.py' -v
make export-xml
make test-local
```

`native-test` запускает CTest и проверку JSON-контракта CLI на текущей ОС. CTest проверяет все восемь вызовов, ограничение аргументов, обязательные метрики и явные статусы доступности. Python-проверка разбирает массив JSON от `--all-diagnostics`. YAxUnit загружает конфигурацию в 1С, вызывает каждую диагностику отдельно, проверяет пакетный клиентский результат и серверное исполнение/запись результата.

27 ноября 2026 года нативные CTest и Python-проверки прошли на macOS ARM64; CLI/Core отдельно прошли в Linux ARM64 Docker. На macOS доступны 002/003/004/008/009; 005/006/007 вернули ожидаемую причину недоступности API. В Linux ARM64 Docker-VM доступны 002/003/004/005/007/008/009; 006 не обнаружил доступной SMT-пары.

Интеграционный прогон версии 0.3.0 прошёл в файловой ИБ на 1С 8.5.1.1529/macOS x86_64: **102 теста, failures=0, errors=0**. YAxUnit выполнил каждый код CPU_002–CPU_009 отдельно, проверил комплект на клиенте и серверную обработку, а также наличие 16 сохранённых строк. В этом прогоне оценка MHz составила 3198,9 на клиенте и 3196,9 в серверной директиве. В файловой ИБ оба значения относятся к одной машине, а серверная директива не создаёт отдельный кластерный `rphost`. Старый файл компоненты оставался в кэше клиента; версионированный путь из нового манифеста позволил пройти тест без ручной замены кэшированного бинарника. Эти результаты не заменяют runtime-проверку Native API на Linux/Windows.

Платформенные ограничения и обходы сохраняются в [runbook](runbook.md). Лицензии 1С, заголовки SDK и временные отчёты в репозиторий не добавляются.

## Сборка и пакет

Официальные заголовки Native API нужны для библиотек платформ, CLI и unit-тесты собираются без SDK. Полный перечень команд и архитектур — в [development.md](development.md); известные кросс-компиляционные особенности — в [runbook](runbook.md#уже-встречавшиеся-проблемы).

```bash
make native-core
make native-test
NATIVEAPI_INCLUDE_DIR="/путь/к/VNCOMPS/include" make native-linux-arm64
NATIVEAPI_INCLUDE_DIR="/путь/к/VNCOMPS/include" make native-windows-x86_64
NATIVEAPI_INCLUDE_DIR="/путь/к/VNCOMPS/include" make native-macos-arm64
make native-package NATIVE_TARGETS="linux-arm64 linux-x86_64 linux-i386 windows-x86_64 windows-i386 macos-x86_64 macos-arm64"
```

Пакет Native API 0.3.0 находится в [`CpuFrequencyProbe-0.3.0.zip`](../releases/CpuFrequencyProbe-0.3.0.zip); контрольная сумма — в соседнем `.sha256`. Он собран для Linux x86/x86_64/ARM64, Windows x86/x86_64 и macOS x86_64/ARM64. Успешная компиляция проверяет ABI и таблицу экспорта, runtime надо подтверждать отдельно на целевой 1С/ОС.
