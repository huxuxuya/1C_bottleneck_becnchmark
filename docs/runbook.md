# Практический runbook разработки

[Главная](../README.md) · [Подробная инструкция](development.md) · [Каталог проверок](tests/README.md) · [Native API CPU](native-cpu-probe.md)

Эта памятка фиксирует команды, расположение исходников и решения проблем, уже встречавшихся при разработке. Она дополняет [инструкцию по сборке и запуску](development.md): здесь отмечено, что реально проверено, что требует локальных дистрибутивов/лицензии и где прогон пока не завершён.

## Короткий маршрут

Для обычной правки BSL или конфигурации на машине с установленными EDT и 1С:

```bash
set -e
make export-xml
make test-local
```

`make export-xml` переносит проекты EDT в XML. `make test-local` пересоздаёт файловую ИБ в `build/ib-local-test`, устанавливает расширения тестов и запускает YAxUnit пакетно. Кнопку обработки нажимать не нужно. Отчёты появятся в `build/reports/`.

27.11.2026 после свежего `make export-xml` локальная 1С 8.5.1.1529 прошла **111/111 тестов, 0 failures, 0 errors** и полным `1cv8`, и тонким `1cv8c`; это отдельные файловые ИБ. Бинарник платформы x86_64 работает на macOS ARM64. Отчёты находятся в `build/reports-local-native06-full-after-export/` и `build/reports-local-native06-thin-after-export/`. Файловый прогон не подтверждает работу отдельного серверного процесса `rphost`.

### Где запускается проект и где тестировать

- Исходники редактируются в проектах EDT `edt/benchmark` и `edt/BenchmarkTests`. После правок выполнить `make export-xml`; результат для запуска — `build/xml/`.
- Автоматические локальные прогоны используют отдельные файловые ИБ под `build/ib-*`. Например, `make test-local` пересоздаёт `build/ib-local-test`; команды полного и тонкого клиентов ниже создают свои базы и отчёты `build/reports-local-native06-full-after-export/` и `build/reports-local-native06-thin-after-export/`. Не направлять скрипт на пользовательскую ИБ: выбранный `IB_DIR` удаляется перед созданием.
- На 27.11.2026 EDT Designer AgentMode был подключён к существующей файловой ИБ пользователя. Для проверки уведомления использовалась отдельная база; исходная ИБ оставлена без изменений. Попытка прочитать `.dt` через `ibcmd infobase dump` завершилась отказом `Ошибка блокировки информационной базы для конфигурирования. Возможно, информационная база уже открыта Конфигуратором.`
- Отдельная локальная ИБ для Native API и YAxUnit: `build/ib-local-native-popup-check`; данные автономного сервера: `build/ibcmd-data-local-native-popup-check`. Создана `ibcmd` 8.5.1.1529 из свежего `build/xml/cf`; установлены расширения `BenchmarkTests` и `YAXUnit`. Полный пакет на `1cv8` 8.5.1.1529/macOS x86_64 прошёл **111/111 тестов, 0 failures, 0 errors**. Отчёты: `build/reports-local-native-popup-check/`.
- Для ручного запуска этой базы в режиме предприятия используйте:

  ```bash
  /opt/1cv8/8.5.1.1529/1cv8 ENTERPRISE \
    "/F$PWD/build/ib-local-native-popup-check"
  ```

  После открытия конфигурации вручную открыть обработку «Запуск бенчмарка» и нажать нативную CPU-кнопку. Этот визуальный smoke-check пока не выполнен.
- Чтобы заново подготовить эту же изолированную ИБ и прогнать YAxUnit, используйте шаблон ниже. Сценарий удаляет и создаёт заново именно заданный `IB_DIR`; сохранённые данные этой тестовой базы будут сброшены.

  ```bash
  set -e
  make export-xml
  make download-yaxunit
  PATH="/opt/1cv8/8.5.1.1529:$PATH" \
  CLIENT_BIN="/opt/1cv8/8.5.1.1529/1cv8" \
  WORKSPACE="$PWD" \
  IB_DIR="$PWD/build/ib-local-native-popup-check" \
  REPORTS_DIR="$PWD/build/reports-local-native-popup-check" \
  ./tools/scripts/build-and-test.sh --mode ibcmd
  ```

- Обычные BSL/YAxUnit-прогоны используют отдельные scratch-ИБ под `build/ib-*`. `make test-local` пересоздаёт только `build/ib-local-test`; для тестов, требующих сохранения отдельной базы, задавайте уникальные `IB_DIR` и `REPORTS_DIR`.

### Постоянная рабочая ИБ проекта

Для ручной работы и интерактивной проверки создана файловая ИБ `local/onec/benchmark` с отдельным каталогом данных `local/onec/benchmark-server-data`. Она подготовлена на 1С 8.5.1.1529 из текущего `build/xml/cf` и содержит расширения `BenchmarkTests` и `YAXUnit`. Каталог `/local/onec/` исключён из Git и не очищается командами сборки из `build/`.

На этой же постоянной ИБ выполнен полный YAxUnit-пакет: **111/111 тестов, 0 failures, 0 errors**. Отчёты: `build/reports-local-workbench/`. Это подтверждает подготовку конфигурации, но не проверяет вручную всплывающее уведомление: для него нужно открыть форму в интерфейсе и нажать нативную CPU-кнопку.

Открыть базу в режиме предприятия:

```bash
./tools/scripts/run-local-workbench.sh
```

Чтобы обновить её после изменения основной конфигурации, сначала закрыть все сеансы этой ИБ, затем экспортировать проект и загрузить XML:

```bash
make export-xml
IBCMD=/opt/1cv8/8.5.1.1529/ibcmd
"$IBCMD" infobase config import \
  --db-path="$PWD/local/onec/benchmark" \
  --data="$PWD/local/onec/benchmark-server-data" \
  "$PWD/build/xml/cf"
"$IBCMD" infobase config apply \
  --db-path="$PWD/local/onec/benchmark" \
  --data="$PWD/local/onec/benchmark-server-data" \
  --force
```

Эту постоянную ИБ не передавать как `IB_DIR` в `build-and-test.sh`: сценарий удаляет выбранный каталог и создаёт базу заново. Для автоматического пакета использовать отдельную ИБ в `build/`, как `build/ib-local-native-popup-check`.

Бинарники в `/opt/1cv8` не находятся через обычный `PATH`; скрипт сборки умеет искать их в этом каталоге. При автоматическом поиске `ibcmd` первым находится 8.3.24.1342, поэтому для теста на 8.5.1.1529 закрепите обе утилиты: поставьте каталог версии первым в `PATH` и задайте `CLIENT_BIN`. Блок ниже запускает полный и тонкий клиенты по очереди и останавливается при первой ошибке.

```bash
set -e
make export-xml
make download-yaxunit
PATH="/opt/1cv8/8.5.1.1529:$PATH" \
CLIENT_BIN="/opt/1cv8/8.5.1.1529/1cv8" \
WORKSPACE="$PWD" \
IB_DIR="$PWD/build/ib-local-native06-check" \
REPORTS_DIR="$PWD/build/reports-local-native06-check" \
./tools/scripts/build-and-test.sh --mode ibcmd

PATH="/opt/1cv8/8.5.1.1529:$PATH" \
CLIENT_BIN="/opt/1cv8/8.5.1.1529/1cv8c" \
WORKSPACE="$PWD" \
IB_DIR="$PWD/build/ib-local-native06-thin-check" \
REPORTS_DIR="$PWD/build/reports-local-native06-thin-check" \
./tools/scripts/build-and-test.sh --mode ibcmd
```

Для 8.3.24.1342 замените версию во всех путях `PATH` и `CLIENT_BIN`. Указывайте отдельные `IB_DIR`: скрипт очищает выбранную папку перед созданием тестовой базы.

На этом же хосте установлен Docker Engine 20.10.22 и работает отдельный стенд ARM64 с клиентом 1С 8.5.1.1529, сервером 1С, RAS, PostgreSQL, сервисом лицензирования и веб-сервером. Он не относится к Compose-конфигурации проекта в `docker/docker-compose.yml`; тесты этого репозитория в нём не запускались. Не регистрировать там тестовые ИБ и не менять данные стенда. Для отдельного `rphost` использовать изолированный тестовый кластер проекта или явно выделенный стенд.

ARM64 клиентский образ проверен в одноразовом контейнере без сети: архитектура `aarch64`, `1cv8c` находится в `/opt/1cv8/arm64/8.5.1.1529/`, `xvfb-run` установлен, `ibcmd` в образе нет. Runtime клиента и каталог `~/.1cv8` предоставлялись отдельными томами; в `ExtCompT` при read-only осмотре обнаружен только пустой `registry.xml`, без установленного `CpuFrequencyProbe`. В смонтированном каталоге лицензий найден `.lic` файл, но действительность лицензии и её получение клиентом не подтверждены.

Отдельный сервис лицензирования был доступен только внутри сети стенда. ARM64 клиент с локальной файловой ИБ запускался как без сети, так и в этой сети; в обоих случаях он завершился до YAxUnit с `Цифровая подпись конфигурации неверна`. Получение клиентской лицензии не подтверждено.

Серверный ARM64 образ предоставлял `ibcmd` 8.5.1.1529 по `/opt/1cv8/arm64/8.5.1.1529/ibcmd`; в клиентском образе этой утилиты нет. Одноразовый контейнер с серверным образом и read-only runtime-томами использовался с `--network none` для создания отдельных файловых ИБ, включая ИБ из актуального `make export-xml`, в `build/ib-linux-arm64-native06-*`. Импорт конфигурации и YAxUnit проходили, но клиент завершался до тестов; в `platform.log` записано `Цифровая подпись конфигурации неверна`. Повторный запуск на новой файловой ИБ дал тот же результат. Отчёты: `build/reports-linux-arm64-native06-after-export/` и `build/reports-linux-arm64-native06-with-license-proxy/`.

`xvfb-run` в одноразовом ARM64-контейнере завис на ожидании готовности Xvfb и не запускал `1cv8c`. Ручной запуск `Xvfb :99` позволил запустить клиента; в `platform.log` появилось сообщение о неверной цифровой подписи конфигурации. Источник сообщения не установлен. Если одноразовый контейнер запускает образ с подключёнными read-only томами через `--volumes-from`, переопределяйте его entrypoint: штатный entrypoint пытается менять владельца файлов этих томов и прекращает запуск.

Кэш внешних компонент полного клиента находится в `~/.1cv8/1C/1cv8/ExtCompT`. До диагностической проверки там были `CpuFrequencyProbe_MacOS64.dylib` и запись на это имя в `registry.xml`; после теста исходные файлы кэша восстановлены. Встроенный в проект пакет 0.6.0 использует версионированное имя `CpuFrequencyProbe_MacOS64_v0_6_0.dylib`. Подробности ошибки тонкого клиента — в [статусе Native API](native-cpu-probe.md).

Изменённые исходники сначала экспортируются в `build/xml`, и именно этот экспорт импортирует `ibcmd`. Если экспорт не повторить, тест может запускаться на предыдущем BSL-коде.

## Локальная файловая база

Нужны совместимые `ibcmd` и `1cv8`/`1cv8c`, доступные через `PATH` или `/opt/1cv8`, а также лицензия 1С для клиентского запуска.

```bash
set -e
make export-xml
make test-local
```

Обычная команда `make test-local` каждый раз удаляет и заново создаёт только `build/ib-local-test`. Если эту папку нужно сохранить или требуется изолированный прогон, задайте отдельные каталоги:

```bash
set -e
make export-xml
make download-yaxunit
WORKSPACE="$PWD" \
IB_DIR="$PWD/build/ib-local-cpu-check" \
REPORTS_DIR="$PWD/build/reports-local-cpu-check" \
./tools/scripts/build-and-test.sh --mode ibcmd
```

**Не задавайте `IB_DIR` на существующую пользовательскую ИБ:** скрипт в режиме `ibcmd` очищает заданный каталог перед созданием базы.

Если версия клиента не находится автоматически, укажите её явно:

```bash
set -e
make export-xml
make download-yaxunit
PATH="/opt/1cv8/8.5.1.1529:$PATH" \
CLIENT_BIN="/opt/1cv8/8.5.1.1529/1cv8" \
WORKSPACE="$PWD" \
IB_DIR="$PWD/build/ib-local-cpu-check" \
REPORTS_DIR="$PWD/build/reports-local-cpu-check" \
./tools/scripts/build-and-test.sh --mode ibcmd
```

Скрипт находит `ibcmd` и клиент через `PATH` или в `/opt/1cv8`. Клиент и `ibcmd` должны быть совместимы по версии. На macOS в этом окружении рабочие файлы платформы лежали в `/opt/1cv8/8.5.1.1529/`.

### Уже подготовленная ИБ

Если база уже содержит актуальную конфигурацию, `BenchmarkTests` и YAxUnit, `ibcmd` повторно не нужен. Создайте конфигурацию запуска YAxUnit и запускайте клиент напрямую; готовый пример есть в [development.md](development.md#запуск-в-уже-подготовленной-локальной-иб-без-ibcmd). Для видимых сообщений `Сообщить()` добавьте `/Out <файл> -NoTruncate`.

## Docker

В репозитории подготовлены два режима:

| Цель | Команда | Результат |
|---|---|---|
| Файловая ИБ | `make test-ibcmd` | `ibcmd` и клиент в контейнере, без отдельного `rphost` |
| PostgreSQL и кластер | `make test-postgres` | Клиент подключается к кластеру 1С, данные находятся в PostgreSQL |

Перед первым запуском подготовьте `.env` и выберите способ экспорта XML. Для EDT, установленной на этой машине:

```bash
cp .env.example .env
make export-xml
```

Для Docker-экспорта сначала положите дистрибутив EDT в `docker/dist/edt/`, затем соберите образ и экспортируйте проекты:

```bash
cp .env.example .env
make build-edt
make export-xml-docker
```

`docker/dist/` в Git пуст. Чтобы собирать штатные образы с Ubuntu, положите разрешённые к использованию пакеты платформы 1С `.deb` в `docker/dist/`; для экспорта EDT нужны её файлы в `docker/dist/edt/`. Альтернатива — заранее собранный образ с нужными бинарными файлами платформы. Одного изменения имени `ONEC_IBCMD_IMAGE` недостаточно, если Dockerfile всё ещё собирается от чистого Ubuntu без `.deb`.

После подготовки дистрибутивов:

```bash
make build-ibcmd
make test-ibcmd
```

Для клиент-серверного режима нужны подходящие образы раннера и сервера, PostgreSQL-образ с необходимым для 1С расширением `mchar`, рабочая лицензия и свободные порты `5432`, `1540–1541`, `1545`, `1560–1591`:

```bash
make build-ibcmd
make build-postgres
make up-postgres
make test-postgres
```

В Compose по умолчанию указан `postgres:16-bookworm`. В проведённой попытке этот образ не содержал `mchar`, поэтому создание базы 1С не завершилось. Перед повтором проверьте, что выбранный `POSTGRES_1C_IMAGE` предоставляет `mchar`; наличие PostgreSQL само по себе не означает совместимость с 1С.

Каждый новый запуск с `ibcmd --create-database` требует свободного имени `PG_DB`. Повтор с уже созданной БД может завершиться ошибкой. Для независимого прогона задайте новое значение `PG_DB`. `docker compose ... down -v` удаляет данные PostgreSQL, `srvinfo` и volume лицензий — используйте его только для одноразового стенда.

### Лицензия в контейнере

Compose создаёт volume `1c-licenses` и подключает его к раннеру и серверу. Сам факт существования volume не означает, что он заполнен лицензией. Проверяйте именно volume, связанный с тестовым Compose-проектом, и используйте только штатную лицензию, которую разрешено подключать к этому стенду. Не копируйте лицензии из других активных Docker-проектов и не добавляйте их в Git.

Подтверждённый симптом пустого volume: клиент 1С завершается до открытия базы с текстом `Файл программной лицензии не найден`; `junit.xml` и `exitcode.txt` не создаются. Это означает, что YAxUnit ещё не стартовал. Сначала настройте лицензию, затем повторяйте тест.

После проверки можно остановить тестовые сервисы без удаления volumes:

```bash
make down
```

Не используйте `down -v`, если данные тестовой БД или лицензии нужно сохранить.

## Native API: сборка и проверка

Изменения C++ вносятся в `native/cpu-frequency/`. Переносимое ядро и CLI собираются без SDK 1С; для библиотек Native API нужны официальные заголовки VNCOMPS в `NATIVEAPI_INCLUDE_DIR`.

```bash
make native-core
NATIVEAPI_INCLUDE_DIR="/путь/к/VNCOMPS/include" make native-linux-arm64
NATIVEAPI_INCLUDE_DIR="/путь/к/VNCOMPS/include" make native-linux-x86_64
NATIVEAPI_INCLUDE_DIR="/путь/к/VNCOMPS/include" make native-windows-x86_64
NATIVEAPI_INCLUDE_DIR="/путь/к/VNCOMPS/include" make native-macos-arm64
```

Переносимые CPU-диагностики можно проверить на текущей ОС без SDK 1С:

```bash
make native-test
```

Target собирает C++ ядро и CLI, запускает CTest для кодов `CPU_002_…`–`CPU_010_…` и проверяет JSON всего пакета. На текущей ОС тест проверяет и валидные ответы `Недоступно`, когда API этой платформы не предоставляет источник. После изменения BSL-интеграции дополнительно выполните `make export-xml && make test-local`.

Linux/Windows cross-build запускается через Docker; macOS собирается на macOS с Xcode SDK. Сборка бинарника не доказывает, что компонент загрузится в 1С: нужна runtime-проверка соответствующей ОС/архитектуры. На клиенте и сервере загружаются разные платформенные процессы, поэтому компоненту нужно проверить отдельно на клиенте и на каждом серверном узле, куда может попасть вызов.

Для измерений смотрите не только `yaxunit.log`: сообщения `Сообщить()` попадают в `platform.log`. В `build-and-test.sh` для этого включены `/Out` и очистка старого `platform.log` перед каждым запуском. Найти значения CPU-пробы можно так:

```bash
rg 'CPU_NATIVE_VALUES' build/reports/platform.log
```

Маркер имеет формат `CPU_NATIVE_VALUES|client=...|server=...`. Значения `client` и `server` в файловом режиме получены на одной машине: серверный вызов там не измеряет отдельный процесс кластера `rphost`.

## Отчёты и критерии успешного прогона

| Файл | Что в нём |
|---|---|
| `junit.xml` | Количество выполненных проверок, failures и errors |
| `exitcode.txt` | Код завершения YAxUnit; `0` — успешное выполнение |
| `yaxunit.log` | Старт YAxUnit, перечень тестов, ошибки инициализации/сценариев |
| `platform.log` | Сообщения платформы, в том числе диагностические `Сообщить()` |

Считать запуск успешным только если клиент реально стартовал, `exitcode.txt` равен `0`, JUnit содержит ожидаемое число тестов, а `failures` и `errors` равны нулю. Отсутствие JUnit — не успех и не результат «0 ошибок»: ищите причину до запуска YAxUnit в `platform.log`, Docker logs и состоянии лицензии.

Для проверки BSL-компиляции нужен реальный запуск платформы с загрузкой конфигурации. Python-проверки связей формы и экспорт EDT сами по себе встроенный язык не компилируют.

`make clean` удаляет `build/ib`, `build/xml`, `build/edt-workspace`, `build/reports` и `build/techlog`. Целевые каталоги пользовательских прогонов вроде `build/ib-local-test` и `build/reports-local-cpu-check` этой командой не очищаются; `make test-local` пересоздаёт именно `build/ib-local-test` при следующем запуске.

Повторный file-mode запуск в отдельной сетевой среде тоже не помог. В смонтированном каталоге найден `.lic` файл, получение лицензии не подтверждено. Для стороннего образа проверить зависимости и наличие `fc-list` | Причина подтверждена; штатный Dockerfile содержит зависимость |
| MinGW сборка не поддерживает `std::thread` / не находит `pthread_create` | В Docker-образе выбран вариант GCC MinGW с win32 threading runtime. Переключить Windows toolchain на `g++-posix`; после смены компилятора удалить старый `build/native/windows-*`, чтобы CMake не продолжил использовать закэшированный компилятор. Для статической DLL добавить `-static -static-libgcc -static-libstdc++` и проверить импорты через `x86_64-w64-mingw32-objdump -p` или `i686-w64-mingw32-objdump -p`; итог не должен требовать `libwinpthread-1.dll` | Проверено кросс-сборкой x86/x86_64; Windows runtime отдельно не прогонялся |
| Linux ARM64 диагностика 006 недоступна в контейнере | Виртуальная машина/контейнер не показывает SMT-соседа вместе с отдельным физическим ядром. Это ограничение доступной топологии, а не ошибка расчёта; проверить `/sys/devices/system/cpu/cpu*/topology/thread_siblings_list` и разрешённый CPU set на целевой машине | Повторено в ARM64 Docker: другие доступные тесты прошли, 006 сохранил ясный статус недоступности |
| Клиент 1С сообщает `Тип не определен` для второго класса Native API | В текущем стенде фабрика напрямую создавала оба имени, но клиентская платформа не регистрировала дополнительный `CpuDiagnostics`. Передача строкового кода диагностики в существующий `Measure` тоже не сработала: числовые значения по умолчанию Native API применялись до вызова C++. Для совместимости оставить один класс `CpuProbe`, а диагностики передавать внутренними отрицательными целыми `-2` … `-10`; `-1` означает комплект. Снаружи сохранять именованные коды `CPU_002_…` … `CPU_010_…`. Подтверждать именно интеграционным YAxUnit-тестом, который загружает компоненту в 1С | Практический обход для текущей платформы; отдельный класс не использовать без runtime-проверки |
| После обновления Native API клиент 1С продолжает вызывать старую сборку | Клиент хранит извлечённую библиотеку в `~/.1cv8/1C/1cv8/ExtCompT/`. Воспроизведено: пакет и свежая ИБ содержали новый x86_64-бинарник, но клиент вызвал закэшированный файл от 26 ноября. Замена именно `CpuFrequencyProbe_MacOS64.dylib` на собранную библиотеку дала успешный прогон. Затем восстановили старый кэш и проверили версионированные имена из `MANIFEST.XML` (`..._v0_3_0...`): свежая ИБ прошла 102/102 теста, и в таблице сохранились клиентские и серверные результаты. При выпуске обновления включать номер версии в имена библиотек, проверять `Template.bin` и тестировать обновление при сохранённом старом `ExtCompT` | Подтверждено на клиенте 1С 8.5.1.1529 с macOS x86_64; старый файл оставался в кэше во время успешного теста версии 0.3.0 |
| Клиентская Native API DLL отсутствует для macOS x86_64 | Установленная локальная платформа 1С — Mach-O x86_64 под Rosetta, даже на ARM-машине. В общий макет должны попасть одновременно `macos-x86_64` и `macos-arm64`; ориентироваться на архитектуру процесса 1С, не только на `uname -m` | Проверено по `file /opt/1cv8/.../1cv8c`; обе macOS архитектуры должны оставаться в EDT-пакете |

| Серверный CPU-замер проходит в файловой ИБ, но не в Docker-кластере | В файловом режиме директива `&НаСервере` не создаёт отдельный `rphost`. Для кластерного значения нужны клиент, действующая лицензия и серверный Native API бинарник | Ограничение архитектуры подтверждено; отдельное число `rphost` требует лицензированного стенда |

## Подготовка релиза `.cf`

Релиз собирается из EDT-исходников через свежий XML-экспорт и отдельную временную ИБ. Не сохранять `.cf` из пользовательской или старой рабочей ИБ.

1. Поднять версию конфигурации в `edt/benchmark/src/Configuration/Configuration.mdo`. Если менялась Native API, обновить `project(... VERSION ...)` в `native/cpu-frequency/CMakeLists.txt`, собрать нужные архитектуры через `make native-*` и создать ZIP через `make native-package`. Если Native API не менялась, оставить её версию и существующий проверенный ZIP без изменений.
2. Экспортировать EDT, создать пустую релизную ИБ, загрузить в неё основной XML и применить конфигурацию:

   ```bash
   make export-xml

   RELEASE_VERSION=0.0.6-alpha
   IBCMD=/opt/1cv8/8.5.1.1529/ibcmd
   RELEASE_IB="$PWD/build/ib-release-$RELEASE_VERSION"
   RELEASE_CF="$PWD/releases/1C-Bottleneck-Benchmark-$RELEASE_VERSION.cf"

   "$IBCMD" infobase create \
     --db-path="$RELEASE_IB" \
     --data="$RELEASE_IB/server-data" \
     --locale=ru
   "$IBCMD" infobase config import \
     --db-path="$RELEASE_IB" \
     --data="$RELEASE_IB/server-data" \
     "$PWD/build/xml/cf"
   "$IBCMD" infobase config apply \
     --db-path="$RELEASE_IB" \
     --data="$RELEASE_IB/server-data" \
     --force
   "$IBCMD" infobase config save \
     --db-path="$RELEASE_IB" \
     --data="$RELEASE_IB/server-data" \
     "$RELEASE_CF"
   ```

   Использовать новую пустую папку `RELEASE_IB` для каждой сборки. `ibcmd infobase create` не должен получать существующую ИБ; не направлять этот процесс на `local/onec/benchmark` или `InfoBase_empty`.
3. Посчитать SHA-256 для `.cf` и записать его sidecar-файлом:

   ```bash
   shasum -a 256 "$RELEASE_CF" > "$RELEASE_CF.sha256"
   ```

4. Создать `releases/<version>.json` по формату предыдущего манифеста: версия и канал, версия конфигурации, путь и SHA-256 `.cf`, версия/путь/SHA-256 Native API ZIP и версия платформы, которой сохранён `.cf`. Обновить ссылки на релиз в README.
5. Если исходники не закоммичены, не записывать фиктивный `sourceRevision`. После коммита можно добавить его hash в манифест. Не коммитить `.dt` и временную релизную ИБ.

## Как пополнять runbook

Когда находится решение повторяемой проблемы, добавить строку в таблицу выше: наблюдаемый текст ошибки, доказанная причина, минимальная рабочая команда/изменение, способ проверки и ограничения. Если причина не установлена, пометить её как неизвестную, как для `Ошибка формата потока`; не записывать догадку как исправление. Не сохранять в Git лицензии, пароли, приватные `.env` и пользовательские дампы.
