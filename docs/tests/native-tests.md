# Тесты внешней компоненты (Native API)

[Каталог проверок](README.md) · [Тесты платформы (BSL)](bsl-tests.md) · [Сборка Native API](../native-cpu-probe.md) · [Статус реализации](implementation-status.md)

В этом списке собраны проверки из каталога `001–090`, которые должны выполняться **нативным кодом на C++ внутри внешней компоненты 1С (Native API)**. Компонента работает непосредственно в адресном пространстве клиента 1С или рабочего процесса сервера `rphost`, имеет доступ к монотонным наносекундным часам, потокам ОС, привязке к ядрам (`affinity`), сырому файловому I/O (`O_DIRECT` / `fsync`), памяти процесса и сокетам.

- Тесты, отмеченные как **Парный (Native + BSL)**, позволяют отделить аппаратное ограничение от накладных расходов платформы 1С.
- Тесты, отмеченные как **Внешний контур (вне Native API)**, требуют привилегий гипервизора (ESXi), драйвера СУБД или терминального сервера — они оставлены в таблице для полноты покрытия `001–090` с честным указанием границы.

## Дополнительный метод компоненты: системный паспорт

`GetSystemInfo()` не относится к пробам каталога `001–090`, но добавлен в Native API версии 0.4.0 и сохранён в 0.6.0. Он возвращает JSON schema v1 со сведениями об ОС, архитектуре, модели машины, CPU, памяти и видимых лимитах cgroup/Job Object. Форма бенчмарка вызывает метод в клиентском и серверном контекстах и сохраняет ответы в `ПаспортаСистем`.

| Область | Статус | Примечание |
|---|---|---|
| Реализация и сборка для платформ | **Пакет 0.6.0 собран и встроен** | В ZIP входят Linux i386/x86_64/ARM64, Windows x86/x64, macOS x86_64/ARM64. Linux ARM64 CTest/JSON прошли; полный пакет прошёл 103 YAxUnit-теста на macOS x86_64/1С 8.5.1.1621. Runtime в Linux/Windows 1С и отдельный `rphost` ещё не проверены. |
| Вызов и запись паспорта из клиента и сервера | **Пройдены на macOS x86_64, 1С 8.5.1.1621** | YAxUnit проверил клиентский JSON schema v1, сохранение клиентского паспорта и флаг успешной записи серверного паспорта. Прогон выполнен в файловой ИБ; отдельный `rphost` не проверялся. |
| Автопроверка JSON-контракта паспорта | **Пройдена на macOS ARM64 и Linux ARM64 Docker** | `make native-test` вызывает Python-проверку обязательных полей schema v1, типов и допустимых `null` через CLI `--system-info`. |
| Полный каталог оборудования | **Не реализован** | GPU, диски, SMART, сетевые адаптеры и подробности модулей RAM не собираются. |

См. [описание Native API и статус интеграции](../native-cpu-probe.md).

## Приоритетный план расширения текущей `CpuFrequencyProbe`

Текущая компонента `CpuFrequencyProbe` уже решает самую сложную задачу — сборку под 7 архитектур и подключение в клиентском и серверном (`rphost`) контекстах. Чтобы быстро закрыть главные слепые зоны, имеет смысл расширять её в 3 шага:

1. **Шаг 1 (Лёгкие системные методы — 1 день):** добавить `GetProcessInfo()` (PID, архитектура, ОС, uptime) и `GetProcessMemory()` (RSS / WorkingSet). Это сразу оживит пробы **`029`, `031`, `032`, `033`, `035`** в связке с BSL.
2. **Шаг 2 (Честный диск — 2–3 дня):** добавить методы для **`036`, `037`, `038` (`fsync`), `040`, `041`** с `O_DIRECT` и расчётом `p50`/`p95`/`p99`. Это закроет главную диагностическую потребность при тормозах транзакций (`059`).
3. **Шаг 3 (Память и CPU в глубину):** добавить pointer-chasing **`018`**, полосу **`019`/`020`**, affinity-сканирование **`013`** и сетевые проверки **`075`/`076`**.
